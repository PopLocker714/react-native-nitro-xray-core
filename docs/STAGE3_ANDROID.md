# Этап 3 — Kill-switch + URLTest (Android)

> Статус: реализовано, все слои компилируются (Kotlin — статически сверено со сгенерированным спеком; TS — typecheck + 40 тестов зелёные). Прогон на устройстве — чек-лист внизу.

## Kill-switch

### Отклонение от плана: `setBlocking(true)` — НЕ kill-switch

План предлагал `Builder.setBlocking(true)`. Это **ошибка постановки**: `setBlocking` задаёт blocking/non-blocking режим I/O для tun fd и не имеет отношения к блокировке трафика. Более того, xray-core сам форсит fd в non-blocking (`unix.SetNonblock` в `proxy/tun/tun_android.go`), так что флаг в любом случае ни на что не влияет.

### Как работает на самом деле

Физика Android VPN: пока tun-интерфейс с маршрутами `0.0.0.0/0` + `::/0` установлен, весь трафик уходит только в него. Если fd никто не читает — пакеты дропаются (blackhole). Значит:

- **Kill-switch = не отпускать tun, когда движок умер.** `XrayVpnService.handleStartFailure`: при включённом флаге tun остаётся установленным, сервис остаётся foreground, JS получает `error` с пометкой `kill switch active: traffic blocked`. Выход — явный `disconnect()` или успешный reconnect.
- **Переключение сервера без окна утечки** (работает всегда, независимо от флага): новый `establish()` вызывается ДО закрытия старого fd — система атомарно заменяет интерфейс (документированная семантика `VpnService.establish()`). Старый tun блэкхолит до момента замены; старый fd закрываем сами (xray-core fd не закрывает — владелец fd приложение, проверено по исходникам `proxy/tun`).
- **Явный STOP всегда сносит всё** — намерение пользователя важнее kill-switch.

### API

```ts
await XrayClient.setKillSwitch(true)   // персистится (SharedPreferences)
XrayClient.isKillSwitchEnabled()        // boolean
```

iOS: методы застаблены (`setKillSwitch` реджектит с понятным сообщением). Реальный механизм iOS — `NEOnDemandRule` + `includeAllNetworks` — второй проход.

### Границы app-level kill-switch (важно для продукта)

Приложение НЕ может блокировать трафик, когда:
- само приложение убито системой (вместе с VpnService);
- пользователь выключил VPN в системных настройках.

Полная гарантия — только системный **Always-on VPN + «Блокировать соединения без VPN» (Lockdown)**: Настройки → Сеть и интернет → VPN → ⚙ рядом с профилем → оба тумблера. Приложение может лишь вести пользователя на этот экран (`Settings.ACTION_VPN_SETTINGS`). В продуктовом UI стоит показать инструкцию при включении kill-switch.

## URLTest (MVP, чистый TS)

```ts
const results = await XrayClient.urlTest(servers, { timeoutMs: 3000, concurrency: 8 })
// results отсортированы: быстрые → медленные → недоступные (null)
```

Семантика **reachability-grade**: HTTP HEAD на `http://address:port`; большинство прокси-серверов ответят протокольной ошибкой — измеряется время до settle (DNS + TCP handshake RTT), это и есть ранжирующий сигнал. Только таймаут = `null` (недоступен). Замер реальной скорости через прокси (xray observatory) — V2 по плану.

Опции: `probeUrl` (кастомный эндпоинт, например health-URL), `fetchFn` (инъекция для тестов).

## Чек-лист прогона на устройстве

1. **Переключение без утечки**: подключиться к A → включить непрерывный пинг на устройстве (`ping -i 0.2 8.8.8.8` в termux или видео-стрим) → переключиться на B → трафик не должен уходить в обход (IP-чекер не должен показать реальный IP ни на миг).
2. **Kill-switch hold**: включить тумблер → подключиться к заведомо мёртвому серверу (или уронить движок) → интернет должен ПРОПАСТЬ полностью (blackhole), в логе `kill switch active: traffic blocked` → Disconnect возвращает сеть.
3. **Kill-switch off**: то же с выключенным тумблером → сервис останавливается, сеть работает напрямую.
4. **Персистентность**: включить kill-switch → убить приложение → открыть → `isKillSwitchEnabled()` = true (тумблер включён).
5. **Ping all**: загрузить подписку → Ping all → список отсортирован, у живых серверов бейдж `NN ms`, у мёртвых `×`.
6. **Регресс**: квота/срок из подписки и непрерывность трафик-счётчика при переключении (этап 2.5) не сломаны.
