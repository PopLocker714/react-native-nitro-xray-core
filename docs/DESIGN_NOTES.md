# react-native-nitro-xray-core — Design Notes & Roadmap

> Живой документ. Фиксируем рассуждения, решения и открытые вопросы.
> Дата старта обсуждения: 2026-07-04.

## Контекст и цель

Илья строит коммерческий VPN-клиент на React Native поверх этой библиотеки. План: опубликовать в App Store / Google Play, монетизация через in-app purchases (подписка на VPN). Требования: стабильность, безопасность (проверка уязвимостей), нормальная документация реализации, поддержка «подписок» (subscription URL / QR как в Happ, v2rayTun, v2rayNG).

Вторая большая задача: интеграция обхода блокировок для мобильного интернета в РФ через olcrtc/olcbox (паразитирование на легальных whitelisted WebRTC-сервисах). Вопрос: отдельный пакет или встраивать.

## Что пакет умеет сейчас (факты из кода)

Нативная поверхность — 6 методов (`src/specs/nitro-xray-core.nitro.ts`):
- `hasVpnPermission()`, `requestVpnPermission()`, `requestNotificationPermission()`
- `isVpnConnected()`
- `startXray(configJson: string)`, `stopXray()`

Архитектура:
- **Config = сырой Xray JSON-стринг**, который напрямую отдаётся в `core.LoadConfig("json", ...)` (см. `go-core/libxray/main.go` / `main_ios.go`). Ядро — полный xray-core (`main/distro/all`).
- Android: `HybridNitroXrayCore.kt` → стартует `XrayVpnService` (VpnService, foreground) → поднимает TUN → `XrayEngine.start(json, tunFd)` через JNI в `libxray.so`.
- iOS: `HybridNitroXrayCore.swift` → пишет config в App Group UserDefaults → `NETunnelProviderManager` → отдельный таргет `PacketTunnelProvider` (пример в `example/ios/tunnel/`) читает config, поднимает TUN, дёргает `StartXray` из `Xray.xcframework`.
- Прекомпилированные бинарники (`libxray.so`, `Xray.xcframework`) закоммичены в репо.

### Важная поправка к постановке задачи
«Поддерживает gRPC/XHTTP, но не всё современное» — на уровне **транспортов это не так**. Раз конфиг сырым JSON уходит в xray-core, доступно ВСЁ, что умеет ядро: VLESS/VMess/Trojan/SS, Reality, XTLS-Vision, gRPC, WebSocket, HTTPUpgrade, XHTTP, mKCP и т.д. Реальный пробел — **не транспорты, а всё вокруг конфига**: парсинг подписок, типобезопасный билдер конфига, статистика, события, замер пинга, kill-switch. Именно «ручек» вокруг ядра не хватает.

## Пробелы и риски (аудит)

### Функциональные пробелы
1. **Нет парсинга подписок.** Ни `vless://` / `vmess://` / `ss://` / `trojan://` URI, ни base64-подписки, ни SIP008, ни Clash/sing-box YAML. Пользователь сейчас обязан руками писать сырой Xray JSON. Это ядро продуктовой ценности (вставил ссылку → куча серверов).
2. **Нет типобезопасного билдера конфига** — сырые строки, легко ошибиться.
3. **Нет статистики трафика** (upload/download/скорость). У xray-core есть StatsService API — не проброшен.
4. **Нет событий состояния соединения.** Только булев поллинг `isVpnConnected`. Нет `onConnected/onDisconnected/onError`, нет стрима логов в JS.
5. **Нет замера задержки/URLTest по серверам** — нельзя выбрать «быстрейший».
6. **Нет per-app routing / split tunnel** наружу.
7. **Нет kill-switch / on-demand** — при обрыве туннеля трафик течёт в открытую (`NEOnDemandRule` на iOS, lockdown/`setBlocking` на Android не реализованы). Для платного VPN это must-have.

### Баги / уязвимости
- **[Android] `startXray` резолвит Promise до реального старта движка.** Метод лишь `startService(...)` и сразу resolve. Если движок упадёт внутри `Thread{}` в сервисе — JS об этом не узнает. `isVpnConnected` читает статический флаг `XrayVpnService.isRunning`, а не реальное здоровье туннеля → возможен рассинхрон и «молчаливый» отказ.
- **[iOS] `isVpnConnected` ломается после перезапуска приложения.** Читает `self.manager`, который заполняется только внутри `startXray` в рамках текущего процесса. После рестарта апки вернёт `false`, даже если VPN поднят. Нужно грузить статус из `NETunnelProviderManager.loadAllFromPreferences`.
- **[iOS] `tunnelFileDescriptor()` перебирает fd 0..256 через getsockopt** — хрупко, берёт первый utun fd (может быть не тот). Стандартный, но грязный приём; лучше брать наибольший utun fd.
- **[Приватность] DNS зашит на Google 8.8.8.8/8.8.4.4** в Android `VpnService.Builder` и в iOS settings. Для антицензурного/приватного продукта это утечка и маркер. Должно быть конфигурируемо и в идеале резолвиться через туннель.
- **[Секреты] iOS config (с UUID, Reality-ключами) лежит в App Group UserDefaults (plist, без шифрования).** Для коммерческого продукта — вынести в Keychain.
- **[Supply chain] Прекомпилированные `.so`/`.a` в репозитории** без воспроизводимой сборки. Для security-продукта — собирать в CI из исходников, публиковать хеши.
- **Нет graceful reload конфига** без полного teardown.

## olcrtc / olcbox — что это и как интегрировать

**olcrtc** (github.com/alananisimov/olcrtc): ядро на **Go**, техника «BB22 using side channels» — тунеллирует трафик, паразитируя на легальных whitelisted WebRTC-сервисах в РФ (Jazz, Telemost, WB Stream, Jitsi). Наружу выставляет **локальный SOCKS5-прокси**. Есть спецификация client URI и subscription-формата.

**olcbox** (Kotlin Multiplatform UI): Android — TUN+proxy через VpnService + локальный SOCKS5 (hev-socks5-tunnel); iOS — proxy mode с локальным SOCKS5 на Swift.

### Ключевой инсайт для интеграции
olcrtc — это **не замена Xray, а транспортная «подложка» под ним**. Оба на Go. Правильная модель — цепочка (chaining):

```
TUN → xray-core (VLESS+Reality outbound)
        └─ streamSettings.sockopt.dialerProxy = "olcrtc-out"
             └─ outbound "olcrtc-out" (socks) → 127.0.0.1:<olcrtc SOCKS5 порт>
                  └─ olcrtc (WebRTC side-channel, обходит carrier white-list)
                       └─ интернет → твой VPN-сервер
```

То есть рукопожатие Xray к твоему серверу само едет внутри WebRTC-канала olcrtc, который у оператора в белом списке. Всё это — **чистый конфиг** (`dialerProxy`), нативного кода для сцепки не нужно, если olcrtc слушает локальный SOCKS5.

### Жёсткое ограничение iOS (определяет архитектуру)
На iOS у приложения **один** Network Extension packet tunnel на процесс, и он под лимитом памяти ~15MB (Jetsam; в коде уже стоит `SetMemoryLimit(14MB)` только под xray-core). **Два Go-рантайма (xray-core + olcrtc) в одном NE-процессе в 15MB — почти нереально.**

Вывод: даже если JS-пакеты держать раздельными, на iOS **нативное ядро должно быть одним Go-бинарником**, линкующим и xray-core, и olcrtc (один Go-рантайм, один NE, один TUN). olcrtc внутри работает в SOCKS-only режиме (TUN владеет xray), сцепка — через конфиг.

**Дополнительный жёсткий факт (не только память):** два независимо собранных Go-архива (`-buildmode=c-archive`) **нельзя слинковать в один процесс** — каждый тащит полный Go-runtime, будут дублирующиеся символы рантайма и конфликт двух планировщиков/GC. Значит merge на уровне Go-исходников — это не оптимизация, а **требование**: один Go-модуль импортит оба пакета и собирается в один c-archive. К тому же один рантайм = оверхед памяти платится один раз (критично для ~15MB NE).

**Уточнение развилки после этого факта:** «нативно вместе» — обязательно всегда. Свободный выбор остаётся только на уровне npm-упаковки поверх единого бинарника:
- **A1. Один npm-пакет**, olcrtc как опциональный подмодуль/entry-point. Проще всего для соло-разработчика, нет боли с общим xcframework.
- **A2. Monorepo с общим нативным пакетом** (`vpn-core-native` = merged бинарник + оба Nitro-спека) + два тонких TS-пакета поверх. Чистое разделение и переиспользование, но больше инфраструктуры.
- ~~A3. Два независимых пакета, каждый со своим бинарником~~ — технически невозможно на iOS (два Go-рантайма в одном NE).

### Развилка (открытый вопрос)
- **A. Раздельные npm-пакеты + общий нативный core.** `react-native-nitro-olcrtc` со своим TS-API, но native — один общий Go build (linked both). Чисто по API, переиспользуемо, но общая сборка. — *предварительная рекомендация*.
- **B. Встроить в этот пакет** как опциональный «Russia bypass» тумблер. Один core всегда, проще память/процесс, но связывает две ответственности и всегда тащит больший бинарник.
- **C. Полностью раздельно (два NE)** — на iOS практически невозможно (один tunnel/процесс). Отпадает.

olcrtc — ранняя alpha, пропускная способность WebRTC DataChannel ограничена, зависит от того, что сервисы остаются в белых списках. → это **опциональный режим для РФ-мобилы**, не дефолтный путь.

### Гейты перед бандлингом
- **Лицензия olcrtc** — проверить перед включением в платный продукт. (xray-core — MPL-2.0: линковка ок, но модифицированные MPL-файлы нужно отдавать исходниками; сам пакет MIT.)
- Юридический риск/политика сторов для anti-censorship — отдельный разговор.

## Предлагаемые направления работ (черновик, до плана)

1. **Харднинг текущего клиента** — починить баги статуса/старта, события, ошибки наружу.
2. **Observability** — стрим статистики (StatsService) и логов, `onConnected/onError`.
3. **Subscription layer (чистый TS)** — парсинг `vless/vmess/ss/trojan` URI, base64-подписки, генерация Xray JSON из распарсенного. Ядро продукта.
4. **Kill-switch / on-demand** — iOS `NEOnDemandRule`, Android lockdown.
5. **URLTest / ping** — выбор быстрейшего сервера.
6. **olcrtc integration** — по выбранной развилке (A/B).
7. **Безопасность/приватность** — Keychain для секретов, конфигурируемый DNS, воспроизводимые CI-сборки бинарников.
8. **Документация реализации** — как устроено, как встроить, iOS NE setup, config-схема.

## Решения (2026-07-04)

- **Приоритет:** Харднинг + подписки. Порядок этапов: (1) баги статуса/старта + события + статистика, (2) слой парсинга подписок + config builder, (3) kill-switch + URLTest, (4) olcrtc.
- **Архитектура olcrtc (уточнено):** **Единый нативный Go-core** (xray+olcrtc в одном c-archive) — обязательно (два Go-рантайма не линкуются + лимит памяти NE на iOS). Упаковка TS — **один npm-пакет** `react-native-nitro-xray-core`, olcrtc как опциональный подмодуль/entry-point (`react-native-nitro-xray-core/olcrtc`). Сцепка — через `dialerProxy` в конфиге. Отдельный npm-пакет отвергнут: при едином бинарнике даёт боль с общим xcframework/дублированием символов ради малой выгоды.
- **Модель API:** Типобезопасный слой сверху (`XrayClient.fromSubscription/connect`), сырой JSON остаётся как escape-hatch (`startRaw(json)`). Обратная совместимость сохраняется.
